# セントログ差分同期：実装前の検証ゲート（2026-11-19）

## 今回の決定
- 現行の本番同期を停止・初期化・一括置換しない。写真/PDF/記録は削除しない。
- 新機能を本番へ直接投入しない。隔離されたテスト環境、旧方式との比較、段階的な稼働で確認する。
- 実装前検証で安全に解決できないケースがあれば、**実装・公開を止め、ユーザーに選択肢を短く提示して相談する**。
- 対象者を「IQ」で区別しない。初回利用・操作経験が少ない・操作が速い・手袋/片手操作・小画面など、実際の操作状況を再現する。

## 現状確認と新方式の必要条件
現行アプリは `sentlog_project_snapshots` に案件単位の `revision` と `payload` を保存し、Supabase Realtime では案件変更の通知がある。これはコメント1件の独立保存と別である。
現行の `record-collaboration.js` はコメント/写真/項目の不変の履歴と競合解決を持つので、この履歴を再利用する。新しい差分同期は専用の永続的な変更履歴（各変更の一意ID、案件ID、図面ID、記録ID、変更対象と元の版、送信元端末、順序番号）と再開位置（cursor）が必要になる。
Realtime通知を受けた端末はその差分を取得・照合。通知が欠落したら復帰時に未取得分を再取得する。**通知だけをデータの唯一の保存元にしない**。
写真・PDF本体は通知本文に載せず、ID/ハッシュ/サイズを配信して必要な端末だけ原本を照合・ダウンロードする。元の原本がPC保管後にクラウドから消えている場合は、PC/保有端末からの再送を待つ。受信完了は端末での原本照合と永続保存が完了してから確定する。

## 実装前検証（必須）
| 領域 | 想定パターン | 合格条件 |
|---|---|---|
| 同時新規 | 2台/3台/10台が同じ図面へ調査点と写真を追加 | 全記録・全写真残存、番号重複なし |
| 同時新規 | 同じ文言/別文言のコメント追記 | 両方残る。重複受信で増殖しない |
| 同時変更 | 同じ項目を同じ値/異なる値に更新 | 同じ値は統合、違えば履歴を残して確認 |
| 同時変更 | ひび割れ幅、部材名、変状名、色、寸法、図形移動、引出線、図面メモ | 別項目なら統合、同項目の競合なら確認 |
| 同時削除 | 記録削除と写真追加、コメント追記、復元 | 編集データを消さず確認待ち |
| ファイル | 写真の追加/削除/復活、同一IDで異なる原本、同時複数撮影 | ハッシュ照合と原本保持、上書き不可 |
| ファイル | PDF差替え、同一図面の異なる差替え、DXF取込み/変更 | 異なる原本・座標変換は自動上書きしない |
| 基本通信 | 通知受信、通知遅延、順序逆転、重複受信、通知欠落 | 冪等・欠損補完・適切な再接続 |
| オフライン | 1分/1時間/数日、圏外中の複数回編集 | 永続キューから送信、未受信差分のみ取得 |
| 異常終了 | 送信前/送信中/サーバー保存後/端末保存途中にブラウザ終了 | 二重記録なし、ローカル原本と履歴を保持 |
| ネットワーク | 低速/短時間で切断/タイムアウト/5xx/429/Realtime切断 | 影響案件だけリトライ、他案件は進行 |
| 順序 | 端末時計がずれている/完全同時/0.1秒差 | 競合判定は編集前の既知版で行う |
| 複数人UI | 連打/二重タップ/何度も保存/戻る/進む/ダイアログ閉じる | 安全な単一送信・保留表示・再確認が可能 |
| 入力操作 | 日本語IME変換中/長文/絵文字/貼付け/下書き中に移動 | 文字欠落・重複追加・勝手な破棄がない |
| 操作環境 | iPhone/iPad/PC、画面縮小、縦横、片手/手袋操作 | 誤タップで他者の記録を消さない |
| 誤操作 | 同じ記録を2人が別の解決方法で確定 | 早い方の判断に依存せず新しい履歴を確認 |
| 権限 | ログイン端末変更/退職端末/別アカウント/RLS | 本来見えない案件は取得不能 |
| 移行 | 新旧バージョン混在、既存の大量案件、旧コメント形式 | 旧記録読み取り維持、混在時の双方向の書込み安全 |
| 復旧 | PC原本保管後の写真再配信、ネット未保存の端末、端末交換 | 原本ハッシュ・受信台帳一致、紛失なし |
| 大量データ | 5,000枚超の写真、100枚超図面、急な大量編集 | 冗長全件取得なし、制限超過なら局所停止・遅延回復 |
| 容量 | 空き容量不足、IndexedDB失敗、ストレージ容量上限 | 受信成功と表示しない、送信側の原本を保持 |
| 履歴保持 | 同じ変更の再送、未送信端末が数週間後に復帰 | 過去差分を失わず安全に追いつける |
| 性能 | アイドル15分、同時10端末での記録追加、低速通信 | ベースラインより無駄な通信低下、通常編集の遅延が許容範囲 |
| 完全性 | 削除・統合・バックアップ復旧前後のID、写真数、ハッシュ | 既存値と一致し、欠損0 |
| UX | 「同期ON」「反映待ち」「競合」の区別、再試行表示 | 原因と次の操作が1画面で分かる |

## 完成前の試験ゲート
1. **既存機能の基準試験**：現在の純粋な共同編集モデルと案件統合を何十ケースも繰り返しテストする（`tests/delta_sync_preflight.test.cjs`）。これは新方式の完成保証ではない。
2. **差分プロトコルの契約試験**：専用の試験DBで変更履歴テーブルと再開位置を検証し、未登録端末のアクセス不可・新旧両方式の整合性を確認する。
3. **通信途絶試験**：通知を故意に落とし、イベントを逆順・重複送信し、再接続で全データが一致することを確認する。
4. **端末耐久試験**：ブラウザ強制終了、アプリ切替、圏外、容量不足、旧バージョン、競合操作を端末・WebKitで確認する。
5. **シャドー比較**：実データを変更しない読み取り専用の新同期で旧方式と同じ結果になることを照合する。原本の削除処理・既存DBの移行はここで動かさない。
6. **段階公開**：内部テスト案件だけで新方式に切り替え、検証→本番全体へ徐々に拡張。即時切戻しと保存済み未送信変更の保護を検証する。

## 事前検証で見つかった、実装前に解決すべき設計課題
- 現行DBには独立した「変更イベントの永続ログ」と「端末ごとの既受信カーソル」が存在せず、差分同期そのものの耐久性をまだ検証できない。
- `sentlog_project_snapshots` の1案件1行を毎回更新する方式から移行する際、新旧アプリ混在の更新をどう保持するか決める必要がある。
- 一時ストレージから削除済みの写真は端末へ即時配信できない。保有端末/PCからの原本照合済み再送を維持する必要がある。
- 現状の定期的な全件確認（写真・PDF・受信待ち）には冗長通信が残っている。新方式の実装時に整合性検査の周期と対象を限定する必要がある。
- 記録上の「削除」や「競合解決」は単なる上書きに変換できない。不変履歴を維持する。
- 古いiPhone/iPadが数週間後に復帰しても、その端末が確認していない変更イベントを無条件に消さない。履歴圧縮の条件が必要。
