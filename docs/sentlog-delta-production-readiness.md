# セントログ差分同期の本番反映判断

確認日: 2026-11-20（日本時間）

## 現在の状態

利用者は修正・再検証の継続と本番反映を指示している。追加の承認待ちではない。図面設定、実アプリの保存経路、写真、PC保管への接続を実装し、本番ビルドに組み込んだ。現在は接続後のコードに対して実画面と実SQLの通し検証を進めている。

PR #114 は新しいコードの検証中はドラフトとする。以前のコミットのCI成功を新しい接続の成功として数えない。現時点で本番DBへの適用、案件の差分同期有効化、mainへのマージ、本番Pages公開は行っていない。

## 実装した接続

| 対象 | 現在の処理 | 確認する動作 |
| --- | --- | --- |
| 図面・案件設定 | 設定を履歴付きの専用記録として保存し、実画面へ投影する。同じ値の競合は候補を保持して画面で選択する | 縮尺、回転、図面名、追加、削除、順序、設定の競合と明示的な解決 |
| 通常の保存 | 実record-storeのDB transactionで画面用記録と再送用の保存意図を同時に確定する。replicaへの永続化を照合して保存意図を完了にする | 保存途中の終了、再起動、圏外入力、切替中の追加編集、再送、別端末からの受信 |
| 保存履歴の容量 | 確定済みの記録コピーを上限付きで整理する。複数案件の変更は全案件の確定を待つ。未割当図面と以前のファイル内容は保護する | 連続入力で全図面JSONのコピーが増え続けないこと、片方の案件だけの確定で削除しないこと |
| 初回の切替 | 案件単位の固定した控え、サーバー基準データ、端末の保存履歴を照合する。途中終了後も同じ控えから再開する | 記録と写真を保持すること、控え作成後の入力を取りこぼさないこと |
| 共有写真 | 実アプリから写真runtimeへ接続し、画面用ファイルと差分用Blobのハッシュ・サイズ・受領行を照合する | カメラ保存、相手端末への配送、再起動、遅い旧受信の混入防止 |
| PC保管 | サーバーが最新履歴から保管payloadを再構築し、head・revision・SHA-256を証明する。既存archiveとcapacity APIが証明を使う | 証明生成、スマホ確認、PC確認、保管確定、容量整理、復旧、案件再開 |
| 保管済み案件 | 読み取りを許可し、新規の保管用証明は再開後に作る | 保管後の読み取りや復旧が不要な更新要求で失敗しないこと |
| PC保管後の容量整理 | 最新のPC照合と保管証明、実Blobのハッシュが一致するコピーを、画面用ファイル・WAL・固定控え・移行控え・写真ストアから解放する | 未送信入力、異なる過去の内容、撮影原本、別案件を保持し、整理直後の自動再取得を防ぐこと |
| 案件全体の復旧 | 正規のPC復旧で保存したファイルだけを、保管証明・内容・保存世代と照合する。案件記録の復元と同じtransactionで証明を再検査する | 途中復旧からの再試行、通常編集の混入拒否、新端末への復旧、通常のWAL再実行と確定 |
| 認証と古いタブ | ログイン世代、案件・端末の範囲、旧DB version、旧remote writerを照合する | 遅い応答や旧保存経路が別のログイン先・新しい記録を上書きしないこと |

`scripts/build_delta_sync.py` を本番の最終ビルドに加え、HTML、service worker、cloud worker、既存renderer、archive、capacityを接続した。部品追加だけの状態とは区別する。

## 検証で見つけた問題と是正

| 検出した問題 | 是正と再検証 |
| --- | --- |
| 500件または4MiBを超える復元・図面削除が送信上限で停止する | 独立した操作を事前検証した複数グループに分け、保存済み部分の続きから再開する。図面間の移動は原子性を維持する。501件、4MiB超、途中終了、再試行、削除後の復元を検証した |
| 分割ソースの末尾改行により、撮影時の保存関数名が途中で切れる | 元のファイル結合境界を修正した。構文検査に加え、実際に結合した保存関数を実行して写真の保存と読み戻しを検証する |
| 旧版DBが写真・図面用DBのversion 1を指定して開く | 共通のversion対応openerを使用する。DXF、台帳、PDF、救出用画面を含む実ファイル読み取りを検証した |
| 正規認証でのSQL COMMIT時に、遅延metadata triggerがprivate表を読めない | private triggerを固定search_pathのSECURITY DEFINERに修正し、利用者の直接実行・表アクセスは許可しない。別接続の実PostgreSQLでCOMMIT、保管競合、孤立記録拒否を検証した |
| 画面用ファイルを削除しても差分保存用の同一コピーが残る | PCの現時点の照合結果と完全な保管一覧に結び付け、実バイトが一致する控えだけを解放する。複数ストア、途中失敗、別ログイン、別タブの書き換えを検証した |
| 案件を端末から外した後、PC復旧用のファイル保存が未送信編集と誤認される | 正規の復旧経路で作られた純粋なファイル保存だけに、実バイトと保存世代を確認した証明を発行する。通常の未送信入力は拒否し続け、復旧後は通常のWAL再実行で確定する |
| 新端末へ復旧した最新のPC保管データを、初期基準以後の新規編集と誤認する | サーバーの固定headまで受信してから保護コピーと比較する。install時に同じ受信範囲を再照合し、受信位置・記録・送信待ち・証跡を同時保存する。実SQLとinstallerで、保管中の追記なし同期・真の未送信編集保持・途中失敗・後続受信を検証した |
| WebKitで同期完了のbinding更新時に、固定控えのFile/Blob再保存が失敗する | 固定控えのバイトを独立した行へ分け、通常の状態更新では写真を再保存しない。旧形式はファイルごとに照合して移行し、部分失敗時は元のbindingを保持する。容量整理は参照先行の照合も同じtransactionで行う |

同一コードの最終CIで、写真の自動受領確認と実容量整理・復旧UIを含めて確認する。途中の成功や別コミットの結果で公開可とは判断しない。現在の残件と結果はPR #114の最新headに記録する。

## 現時点の検証根拠

実record-store、IndexedDB adapter、実installer、replica、設定投影を接続した試験で、保存と再起動、切替中の編集、認証変更、容量整理、控えの範囲、確定後の履歴整理を確認した。

実際の公開SQLと既存archive・management・device・capacity・collaboration SQLを使い、設定履歴の投影からスマホ確認、PC保管確定、容量整理・復旧、再開までの正常経路を検証した。証明の不一致、偽装された権限、古いhead、不完全なファイル一覧、切替失敗時のtransaction rollbackも検証した。

新しいCIには、実際の本番HTMLと永続ブラウザープロファイルを使う `tests/delta_app_ui.py` を追加した。ChromiumとWebKitで2端末を動かし、実PGliteのSQLに接続する。既存のFile/Blobを保存した画面を再起動してから初期切替を行い、その後の設定・コメント・写真は手動同期を呼ばず、自動反映と実バイトの受領確認を待つ。`tests/delta_capacity_app_flow.py` は実容量整理・復旧ボタン、実IndexedDB、合成PCのファイル保存と読み戻しを接続する。写真だけの整理に続き、案件全体の取り外し・PC復旧・手動同期まで行い、元の履歴・原本・相手端末のデータを保持し、復旧だけで新しい履歴が発生しないことを確認する。Auth、StorageのHTTP配送、Realtime通知は合成であり、実会社PCのディスクや物理iPhone/iPadの試験とは区別する。PostgreSQLの別接続による保管・追記・同時再試行の競合試験もCIで実施する。

最新の対象コミットと結果はPR #114とそのコミットのActionsに記録する。公開後はPagesで配信された実ファイルのSHA-256をビルド成果物と照合する。

## 公開の順序

1. 同じコミットで正常経路・終了後の再開・同時編集・保管復旧・既存機能の検証を通す。
2. 既存の管理dispatcherを保持する、初期状態が無効の一つのSQL migrationを組み立てて検証する。
3. SQLを無効のまま導入し、新しいアプリを公開して配信ファイルを照合する。
4. 確認済みの所有者の切替を許可し、各端末の控えと履歴を作ってから案件を切り替える。
5. 公開後の状態を確認し、確認できた範囲と残る実機上の条件を報告する。
