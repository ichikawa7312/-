# セントログ差分同期の本番反映判断

確認日: 2026-11-20（日本時間）

## 判断

新しい差分同期への本番切り替えは未完了で、現時点では公開条件を満たしていない。利用者から本番反映の指示は受けている。追加の承認待ちではなく、実アプリの保存・設定変更・PC保管を新方式へ接続する実装が残っているためである。

PR #114 はドラフトのまま維持する。本番 Supabase の変更、案件の delta 有効化、main へのマージ、GitHub Pages の本番デプロイは実行していない。新しい factory や SQL を実装したことを、実アプリで有効になったこととして扱わない。

## 今回確認できた本番側の前提

本番 Supabase は集計とスキーマを読み取り専用で確認した。ユーザーの写真や全文の記録は取り出していない。

| 項目 | 読み取り結果 | 判断への影響 |
| --- | --- | --- |
| 使用中の案件 | 8 件 | 切り替え対象は案件ごとに確認する必要がある |
| 使用中の記録 | 1,860 件 | 全件に共同編集履歴 version 1 がある |
| 保管済みの記録 | 103 件 | 共同編集履歴がないため、復旧時の引き継ぎ処理が別に必要 |
| 単一記録の大きさ | 256 KiB 超は 0 件 | 今回の集計上はイベントの大きさの制約に該当しない。将来の編集まで保証しない |
| 使用中の図面 | 225 件 | 縮尺・回転・ページ情報などの共有設定も移行対象となる |
| 差分同期テーブル | 未導入 | 新モジュールの追加だけで本番の同期方式は変わらない |

履歴 version の存在確認は、全履歴の意味検証、各端末の未送信データの回収、全写真の配送確認を代替しない。案件ごとの基準ハッシュと端末の控えの照合は、実際の移行時に必要である。

## 今回実装・修正した経路

| 経路 | 実装内容 | 本番接続の状態 |
| --- | --- | --- |
| 記録の移動 | 一つの group ID で複数の記録を端末保存、サーバー確定、受信反映。拒否・再試行・ページ分割でも片側だけ確定しない | モジュールと隔離した SQL・ブラウザー試験。アプリの全 writer への接続は未完了 |
| 旧端末の未送信 move | 確認済みの transport 能力がある場合だけ、照合と初期保存を同じ grouped outbox にする | 実 reader・控え・初期保存の通し試験。切り替えの停止機構は注入した fixture |
| 採番 | 記録から生成する採番カウンターを共有設定変更と誤判定しない。受信結果の表示番号とカウンターを再構成する | 実採番関数・record-store・移動処理を用いた試験 |
| 共有写真 | 実 REST 形式の要求、送信、受信、PC再配信、受領行の照合。端末に保存した Blob のハッシュとサイズを確認してから完了判定する | API provider は合成サーバー。実会社 PC・本番 HTTP 経路への接続は未実施 |
| 写真の表示用保存 | 実 record-store に条件付き保存を追加。別の既存値を上書きせず、中止された転送を旧再試行キューへ戻さない | Node とブラウザーの使い捨て保存先。全旧ファイル writer の停止は未実装 |
| 認証の切り替え | session の世代を照合。ログアウト後の遅い更新応答や写真受信を新しい状態へ適用しない | 同じ token での再ログイン、更新成功・失敗、別画面の変更を合成試験 |
| 保管中の競合 | 新しい編集が旧保管データから漏れ得る競合を検出。新方式と旧保管が安全な投影証跡なしに併用されないよう保護する | 追加の互換性保護を隔離 DB で検証。本番への適用は行わない |

写真 runtime が要求する `assertExclusive()` や bootstrap の `assertLegacyWritesBlocked()` に、根拠なく `true` を渡してはいけない。条件付き `writeFile()` の追加だけでは、原本 DB、撮影途中の控え、復元、直接 Blob 消去、古いタブを含めた停止を実装したことにならない。

## 公開を止めている具体的な未接続箇所

### 1. 案件・図面設定の同期

差分 protocol は記録履歴を扱う。縮尺・回転・図面追加・図面名・順序・ページの非表示や差し替えは、共有 metadata と関連ファイルをまとめる別の契約が必要である。現 bridge はその内容を保持して保存対象外にするため、そのまま通常の `persist()` に接続すると、日常の設定操作が保存できなくなる。

採番カウンターは実装済みの投影で解決したが、それを理由に未知の共有設定まで除外しない。

### 2. 実アプリの保存先切り替え

`setItem()` は export された `batch()` ではなく lexical な `batch()` を呼ぶ。`archiveAtomic()` は builder が追加する。`replaceAll()` と直接ファイル消去も存在する。一つの公開関数を置き換えるだけでは、全編集を同じ差分 outbox に原子的に保存できない。

旧保存と新 replica を別々の DB へ順番に書く実装は、途中終了時の片方だけの確定を解決しない。移行中の編集、再起動時の経路選択、旧タブ、写真の旧再試行、復元時の未送信変更まで含めた実装が必要である。

### 3. PCバックアップ・案件保管

現 PC / archive の保管元は `sentlog_project_snapshots` である。delta の event / head を増やすだけでは、その最新版が既存の保管 payload に含まれない。

旧 archive は prepare 時と finalize 時に snapshot revision / payload を照合する。一方、独立した delta 編集は snapshot revision を進めないため、差分が増えたのに古い payload で保管が確定し得る。競合拒否はデータを守るための保護であり、保管機能の接続完了ではない。必要なのは、保管対象の delta head までが完全に投影・検証されたことを証明する手順である。

### 4. 本番の通し動作

新しい HTML / service worker / cloud worker への読み込み、実 Supabase RPC と認証世代、通知、入力中の草稿・選択・IME の復元まで、一つのアプリとして接続する必要がある。現在の部品試験や本番相当ビルドの成功は、新方式が実際に起動している証明にはならない。

## 検証の扱い

GitHub Actions では最新の PR head に対し、Node、PostgreSQL、Chromium、WebKit、本番相当の旧機能ビルドを実行する。合成サーバーの RPC、隔離 DB、使い捨てブラウザープロファイルの結果であり、物理 iPhone / iPad や会社 PC の実機結果とは区別する。
