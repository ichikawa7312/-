# セントログ差分同期：多角的な検証と公開条件

更新：2026-11-20（日本時間）

## 対象と現在地

PR #114 の未公開試作を対象に、同期順序、端末保存、障害復旧、権限、写真再送を別々に検証する。
本番の Supabase、利用者の端末内データ、会社 PC の保管ファイルは試験で操作しない。
SQL の初期状態は無効のまま。移行を有効化する処理と旧版書込み拒否トリガーの本番設置は含まない。
新しい差分コアと IndexedDB アダプターは本番 HTML に読み込ませていない。

今回の結果を「実機 iPhone を含む完成済みアプリの保証」と読み替えない。
試験の件数は同等の証拠ではない。以下ではモデル試験、実ブラウザ試験、実データベース試験、実機試験を区別する。
最新のコミットに対する CI の完了結果は PR の Checks と実行ログを参照する。過去のコミットの成功を新しいコミットの成功として扱わない。

## 再現して修正した問題

| 観点 | 修正前に再現した問題 | 試作の対策 | 根拠となる試験 |
|---|---|---|---|
| 自動送信 | ローカル変更を保存しても送信開始が予約されない | 保存完了後に送信を予約し、連続した通知はまとめる | `delta_sync_adversarial.test.cjs` |
| 操作の継続 | 通信待ちが次の端末保存を止める | 端末保存とネットワーク処理の待ち行列を分ける | 同上 |
| 保存内容の固定 | 保存受付後の呼出元オブジェクト変更が保存内容を変える | 受付時に入力を複製し、非JSON数値等を拒否する | 同上 |
| 終了・応答遅延 | 終了後の古い応答が未送信状態を変更しうる | 終了した処理を遮断、通信取消と待ち時間上限 | 同上 |
| 保存確認 | 正の番号だけで未送信項目を消す | 案件・変更・端末・図面・記録のIDを応答と照合 | 同上／SQL |
| 保存先の混同 | 利用者・案件・端末を持たない状態を採用できる | 保存先の範囲を固定し、不一致は元データを保護して停止 | 同上／IndexedDB |
| 複数画面 | 古い画面が新しい保存内容を丸ごと上書きしうる | 保存版の一致を同一トランザクションで検査 | IndexedDB |
| データ境界 | UTF-8容量、埋込み写真データ、特殊キー等の検査が不足 | サイズと構造を検査、特殊キーを安全に扱う | JS／SQL |
| サーバー入力 | kind欠落・JSON null・不完全な変更を受理 | 必須項目、型、履歴構造を受理前に検査 | `delta_schema_adversarial.sql` |
| 端末停止・保管移行 | 権限確認と書込みの間に対象状態が変わりうる | 案件・端末の状態をロックして照合 | `delta_schema_lifecycle_races.sh` |
| PC写真送信先 | 異なる案件・写真等の送信先でも送信を試みる | 利用者・案件・写真・送信用識別子を送信前に照合 | `photo_redelivery_adversarial.test.cjs` |
| PC再送の完了 | HTTP成功だけで再送成功と表示しうる | publishedと対象写真IDを確認 | 同上 |
| PC通信停止 | 写真アップロードの待ち時間が無制限 | 90秒で中止し、保管元ファイルを保持 | 同上 |

これらは再現試験で発見した欠陥であり、富士川浄水場の過去の症状の原因を確定したという意味ではない。

## 自動試験の範囲

### 差分コアと既存の共同編集モデル

`node tests/delta_sync_adversarial.test.cjs` は、送信自動開始、通信中の追加入力、終了後の応答、ACK誤認、保存先の混同、通知欠落、再試行、期限切れ、記録別競合、特殊キー、容量境界等を検証する。

`node tests/delta_sync_protocol.test.cjs` は既存19ケースを維持する。以前の「別案件を拒否」ケースは、実際に一覧応答に別案件を混ぜる試験へ修正した。

`node tests/delta_interleavings.test.cjs` は次の組合せを検証する。

- 24の固定乱数種 × 4つの因果順序を守った配信順序＝96通り。
- 3端末がそれぞれ圏外で10件を編集。コメント、写真参照、項目変更を混ぜる。
- 完全同時の時計、100ms刻み、逆向きの時計を使用する。
- 各変更を重複して適用し、元の履歴の和集合との一致を照合する。合計5,760回の適用。
- 同じ項目の3種類の候補を残し、明示的な競合解決後に古い変更を再受信しても解決を戻さない。
- 記録削除、写真追加、コメント変更を6つの順序で組み合わせる。
- 5,088件の写真参照がある記録へのコメント追記が、小さい差分に収まり、全参照を保持する。

写真参照の試験は画像ファイル本体の送受信試験ではない。
完全に順序が壊れたサーバー履歴は、受信位置を進めず異常を示す別試験で扱う。

### 実 IndexedDB とブラウザ

`python tests/delta_indexeddb_browser.py --browser chromium --output release-diagnostics/delta-indexeddb-chromium.json`

`python tests/delta_indexeddb_browser.py --browser webkit --output release-diagnostics/delta-indexeddb-webkit.json`

各エンジンで、使い捨てプロフィール、ループバックの試験ページ、実 IndexedDB を使う。
記録・未送信キュー・受信位置をまとめて保存し、保存中断、容量エラー注入、別の利用者・案件・端末、2画面の同時保存、旧形式・不明形式を消さずに停止する動作を確認する。
差分コアとの接続では、再接続による自動送信、サーバー保存後の端末保存失敗、受信保存の失敗を確認する。
別タブ、圏外の再読込み、ブラウザプロセスを閉じて同じプロフィールで圏外起動するところまで確認する。

この開発用コンテナでは実ブラウザの起動制限・依存不足があるため、実ブラウザの合否は専用 GitHub Actions ジョブで確定する。
モデル用 IndexedDB での成功は実ブラウザ成功の代用にしない。
容量不足は故障注入であり、実際にiPhoneの空き容量を使い切った試験ではない。
試験ページの Service Worker は専用のもので、本番アプリの更新移行を検証したものではない。

### PostgreSQL

専用 CI は使い捨て PostgreSQL 17.12 を起動し、次の順で実行する。

1. `tests/delta_schema_fixture.sql`
2. `docs/sentlog-delta-v1-schema-prototype.sql`
3. `tests/delta_schema_assertions.sql`
4. `tests/delta_schema_adversarial.sql`
5. `tests/delta_schema_parallel.sh`
6. `tests/delta_schema_lifecycle_races.sh`

不正な97種類の入力、正常6形式、未ログイン、匿名、他利用者、無効端末、無効案件、直接書込み、変更ID再利用、整数上限、旧版INSERT/UPDATE/DELETEと案件の付替えを検証する。
`delta_payload_contract.cjs` では実際の共同編集モデルから作った14種類の変更と18種類の不正入力を、同じ内容のままJavaScriptとSQLの両方へ渡し、判定の食い違いを検査する。
24件の同時書込みと8回の同一変更再送では、欠番や重複のない履歴と通知になることを照合する。
保管移行・端末停止と同時に書き込む試験は、別セッションのロック待機と状態再検査を確認する。

ローカルでの補助実行は `tests/delta_schema_pglite.cjs` を使う。これはデータベース接続先を受け取らず、プロセス内の一時DBだけを使う。
PGliteの成功だけで、実PostgreSQLの複数接続による競合を合格にしない。

### PC保管写真の再送

`node tests/photo_redelivery_adversarial.test.cjs` は実際のPC再送スクリプトに、合成REST応答と仮想フォルダーを接続して26ケースを検証する。
フォルダー権限拒否、保管元消失、サイズ不一致、同じサイズの内容違い、パス不一致、異なる送信先、送信途中の利用者変更、HTTPエラー、成功を装う応答、連打、通信停止を含む。

照合するのは、クラウドに登録されたサイズとSHA-256に一致するPC保管ファイルである。
登録ファイルが共有用圧縮画像なら、撮影時の高解像度原本を再送した証拠にはならない。
実際の会社PCでのフォルダー権限、保管ファイルの現在の実在、ブラウザ制約は実機確認を残す。

## 公開前に残るゲート

| ゲート | 合格までに必要な確認 |
|---|---|
| サーバーの履歴整合 | 形式が正しくても、未登録記録・存在しない親履歴・既存履歴の書換え・順序不整合を受理しない。受理した1件で後続の同期を止めない設計を確認 |
| 実接続 | 認証付きのAPI、private Realtime channelの権限、トークン更新、アカウント切替、既存の保存・保管トリガーとの組合せ |
| 旧版からの移行 | 旧 SentlogRecords に未送信の写真と記録を残し、同じ検証用保存領域で新版へ移行。中断・再実行・別端末の変更も保持 |
| 既存の大きな案件 | 初回の基準データ取込みを分割し、5,000枚超の参照を含む案件を処理。256KiBのイベント上限を超える新規記録・長い履歴を安全に移行 |
| 写真本体との整合 | 写真ファイルの永続保存と記録・再送キューの対応を確認。画像がない状態を同期完了と扱わない |
| アプリ全体への接続 | 図面追加・差替え・縮尺・回転・メモ・案件名等の各経路を確認。端末固有の表示設定を他端末へ配信しない |
| iPhone／iPad | 実機で撮影、IME変換、保存直後の終了、画面ロック、アプリ切替、圏外復帰、旧版更新を実施 |
| 会社PC | 検証用フォルダーで実読込みと再送。PCを閉じた間は写真だけ待機、再開後の受信保存まで照合 |
| 長期運用・切戻し | 長期圏外、履歴保持・圧縮、起動しない端末、導入途中の中止。新版で保存した未送信データを失わない |
| 性能 | 現在の試作は案件レプリカ全体を1行で保存する。大量の履歴、低速端末、10台同時使用の実測と保存方式の改善が必要 |

## 判定ルール

保存済みと表示した内容の欠落、他人・別案件への流出、誤った上書き、未保存を完了扱いする表示、写真原本の破損・消失は公開を止める。
復旧待ち・写真待ち・競合待ちを表示でき、無関係の記録や案件を進められることも合格条件とする。
同じ変更が二重適用されず、受信位置は端末の保存完了後にだけ進むことを照合する。
試験で解決できない設計上の問題が残る場合は、その再現条件・影響・選択肢を提示してから導入方針を相談する。

実機確認はテスト版で必要な操作に絞り、ログと保存内容の照合を開発側で行う。アプリ削除や端末の保存領域初期化を検証手順にしない。
